## 2026-07-22 — Four logical backend services in one FastAPI deployment

Auth, Import, Dashboard, and Analytics are logical boundaries inside a single FastAPI
application, not four deployments. **Why:** the same team-size reasoning as ADR-001,
applied to the backend — four deployments would multiply operational surface for a
three-person team with no independent-release need. Graduates to an ADR only if
independent deploy cadence ever becomes the binding constraint.

## 2026-07-22 — The family aggregate default is computed, never stored

Whether a user lands on the family-aggregate or per-member dashboard is derived from a
count of their household members at request time. **Why:** a stored `default_view`
column would go stale the moment family composition changed. One fewer piece of state
that can silently disagree with reality.

## 2026-07-22 — No new dependency for fuzzy scheme matching

Scheme-name matching uses the standard library's `difflib.SequenceMatcher`, and the same
idiom is reused for AMFI TER name matching. **Why:** PRD-01's no-new-dependencies
constraint, and the match quality is adequate at the confidence thresholds in use.

## 2026-07-22 — Two allocation endpoints, deliberately not merged

The Dashboard service keeps its coarse `/household-members/{id}/allocation`
(`by_asset_class`, `by_amc`); the Analytics service adds a granular
`/analytics/household-members/{id}/allocation` (`by_category`, plus `by_amc`
re-exposed). **Why:** different granularities for different surfaces. Recorded because it
reads like a route collision and is not one.

## 2026-07-22 — ARN resolution is on-demand, not scheduled

Distributor-name lookup runs inline when the Import Service first sees an unfamiliar ARN
code, rather than as a scheduled job. **Why:** it is event-triggered by an import, not
time-triggered, and it must never block — the fallback is displaying the raw ARN code.
See ADR-006, which confirms this scoping rather than changing it.

## 2026-07-22 — `relationship` is a fixed enum plus a free-text label for `other`

`self` / `spouse` / `parent` / `child` / `sibling` / `other`, with a free-text label used
only when `other` is chosen. **Why:** structured enough for consistent family-grouping
logic, flexible enough not to force real family shapes into the wrong bucket.

## 2026-07-22 — The CAS PDF is staged in local temp storage, not S3, during processing

Processing reads the uploaded file from local temporary storage with guaranteed
deletion, rather than an S3 upload-then-delete cycle. **Why:** simpler to reason about
and audit, and it avoids a network hop for a file that is meant to be short-lived. This
is a separate question from permanent retention, which ADR-004 settles.

## 2026-07-22 — "100% accuracy" means fixtures, not real-world files

The gain/loss accuracy NFR means 100% of what is computed matches hand-verified
known-answer fixtures. **Why:** claiming 100% of real-world CAS files parse perfectly
would be an unbounded claim. Recorded because the number gets quoted without its
qualifier.

## 2026-08-04 — Alembic migrations are hand-written, never autogenerated

Every migration is written by hand rather than produced by
`alembic revision --autogenerate`. **Why:** autogeneration cannot express the
`RANGE (date)` partitioning branch that `transactions` and `nav_history`
require on PostgreSQL. Once one migration must be hand-written, having two
classes of migration is worse than having one.

## 2026-08-04 — Dialect branching is confined to the two partitioned tables

`transactions` and `nav_history` get dialect-branched DDL; the other thirteen
tables are created directly from the same SQLAlchemy model metadata on both
SQLite and PostgreSQL. **Why:** one column list that cannot drift, rather
than two that can. The branch exists only where the dialects genuinely
differ, which is partitioning and nothing else.

## 2026-08-04 — `transactions.type` is a `VARCHAR` + `CHECK`, not a native enum

A knowingly-taken corner cut, marked in the code with a `ponytail:` comment
naming the ceiling and the upgrade path. **Why:** a native PostgreSQL enum is
materially harder to extend than a `CHECK` constraint, and the
transaction-type vocabulary was expected to grow. Recorded as R-022 so it
reads as deliberate rather than as an oversight.

## 2026-08-04 — The CAS-parser prototype is ported and deleted, not maintained alongside

The standalone prototype backend was retired the moment the tightened logic
was green inside the monolith. Its frontend was deliberately left in place as
reference material for the Phase 1b UI plan. **Why:** two half-alive backends
is the expensive failure mode, not the cost of the port. The prototype had
also been persisting a masked PAN on two tables in violation of the project's
own rule — a permanent guard test (`backend/tests/models/test_no_pan_field.py`)
was left behind whose only job is to fail if a PAN-shaped column ever
reappears. That test is now in tension with ADR-007; see R-018.

## 2026-08-05 — ADR-001 amended, not rewritten, after its premise proved false

ADR-001 claimed the decision preserved in-progress React work; the prototype frontend
turned out to be vanilla TypeScript. An Amendment section was added and the "no rework"
benefit marked moot; the decision itself stands on its other merits. **Why:** vault rule
— supersede and correct in place, never silently rewrite a past record.

## 2026-08-05 — Test sessions must be built with production's `autoflush` setting

A standing rule, not a patch: test database sessions are constructed with the
same `autoflush=False` setting production uses. **Why:** Phase 1's final
review found a real production bug that the test suite had been hiding,
because tests and production differed in exactly this one setting. Built into
the next plan from the start rather than fixed after the fact.

## 2026-08-05 — OTP codes are hashed with SHA-256, deliberately not bcrypt or argon2

Standard-library SHA-256 for OTP codes; session tokens are opaque random
strings stored only as a hash and returned to the client exactly once.
**Why:** OTPs are short-lived, low-entropy codes, not long-lived credentials.
A deliberately slow hash on a six-digit code buys nothing — the attack it
defends against is guessing the code, which rate limiting and expiry address,
not hash cost.

## 2026-08-05 — The Import Review flow is a step enum in one parent component, no router

One stateful parent owns a step enum and the current preview/confirm/error
data; five child screens render off it. No router, no context, no state
library. **Why:** the flow is linear, short-lived and discarded on
completion. A router was explicitly considered and rejected as premature.
This became the pattern for every subsequent flow — see
[frontend composition](../06-architecture/frontend-composition.md).

## 2026-08-05 — Money and unit values cross the API as strings and are never parsed

Amounts, units and NAVs arrive from the API as strings and are displayed
as-is, never converted to a JavaScript number. **Why:** the frontend mirror of
the backend's `Decimal`-everywhere rule. A float conversion in the display
layer defeats the point of never using floats in the calculation layer.

## 2026-08-06 — Every dashboard compute function takes a list of household member IDs

One implementation serves both the per-member view (a one-item list) and the
family aggregate (every member the caller owns). **Why:** two code paths for
the same computation will drift, and the family aggregate is the default
landing view, so the drift would be user-visible. Family-aggregate responses
wrap a per-member status list so a member with no data shows as
present-but-empty rather than being silently dropped.

## 2026-08-06 — Three portfolio-accounting conventions fixed

Cost basis is **FIFO**. An "active" SIP means a contribution inside a
**40-day window**. **Switch transactions are excluded from cash flow.**
**Why:** FIFO matches how Indian mutual-fund units are actually redeemed;
40 days tolerates a late monthly instalment without declaring a stopped SIP
active; a switch moves money within the portfolio rather than in or out of
it, so counting it as a flow would double-count. Securities transaction tax
and stamp duty are deliberately *not* treated as cost-basis-adjusting — see
R-028.

## 2026-08-06 — Coarse allocation belongs to the Dashboard service

The TDD's API-surface table listed the coarse allocation endpoint under
Analytics. Phase 3 recorded that as a documentation slip and placed it in
Dashboard. **Why:** the holdings engine it depends on already lives there.
This agrees with the existing "two allocation endpoints, deliberately not
merged" entry rather than contradicting it — Dashboard keeps the coarse view,
Analytics later adds the granular one.

## 2026-08-06 — Two family-upload constraints, both driven by backend shape

The account holder's own household-member row is resolved **list-then-create,
never blind-create**, and family CAS files are parsed **sequentially, never in
parallel**. **Why:** there is no `PATCH /household-members` endpoint, so a
session resumed after a reload would otherwise insert a duplicate `self` row;
and the backend holds a single in-memory preview per session, so concurrent
parse calls race each other. Both are backend facts expressed as frontend
rules, recorded so no future task treats either as a surprise.

## 2026-08-07 — The distributor-comparison route is member-scoped, not fund-global

`GET /household-members/{id}/distributor-comparison`, correcting the TDD's
fund-level shape. **Why:** a comparison of "your returns by distributor" is
meaningless without knowing whose returns. This contradicts the route
recorded in `05-docs/reference/api-surface.md`; flagged as R-017 rather than
silently corrected.

## 2026-08-07 — Only a definitive ARN lookup outcome is ever cached

Found-with-status and confirmed-not-found are written to the directory table;
a transient failure never is, and no raw third-party response is persisted.
**Why:** the same lesson a NAV-outage bug had already taught in Phase 3,
where a provider outage was cached as a permanent answer. Applied
pre-emptively here rather than after the second incident.

## 2026-08-07 — Frontend implementation is handed out under a written brief with a numeric quality bar

The frontend redesign was packaged as a self-contained brief for an external
coding agent (Google Antigravity): four named design-system gaps, an explicit
split between polishing existing screens and building new ones, three screens
out of scope, an acceptance bar stated as a score on a ten-heuristic
usability rubric, and a requirement that the agent name itself as author.
**Why:** the agent has no access to the team's conversation history, so
anything unstated is unavailable — and authorship needs to stay traceable
afterwards. This worker category is not covered by the orchestration skill
built five days later; see R-029.

## 2026-08-10 — XIRR is a hand-written Newton-Raphson solver on `Decimal`

No numeric library. **Why:** a numeric library would force conversion to
floating point, which the project's money rules forbid, and would add a heavy
dependency for one function. The solver operates purely on `Decimal`.

## 2026-08-10 — The category universe is cached to local disk for 24 hours, not loaded into the database

The only reference integration that does not write to a reference table.
**Why:** the source is a ~1.6MB text file that changes at most daily and is
used as a lookup list rather than joined against. Loading ~90 category
headings into Postgres to re-read them on every request buys nothing. The
trade-off is that a disk cache is process-local — see
[INV-001](../04-investigations/INV-001-category-universe-gap.md), and note
that `05-docs/reference/external-data-sources.md` had to be qualified because
of it.

## 2026-08-10 — Granular analytics allocation re-exposes the coarse view rather than recomputing it

The Analytics allocation response carries the granular `by_category`
breakdown **and** the coarse `by_amc` view, both bucketed from one holdings
computation in a single pass. **Why:** the analytics tab becomes one request
instead of two, and the two views cannot disagree, because they come from the
same numbers. The Dashboard's coarse endpoint was not rebuilt or moved.

## 2026-08-12 — The model-orchestration skill is project-level and classified internal

Not a user-level skill. **Why:** it contains account- and path-specific
detail that should not be published, and the delegation policy it encodes is
this project's, not a general practice. The substantive decision — who
orchestrates, who implements, and that review is mandatory — is
[ADR-011](ADR-011-model-orchestration-and-delegated-implementation.md); this
entry records only the packaging call.

## 2026-08-13 — The FR-7 score breakdown is recomputed on read and never persisted

Return, risk and consistency percentiles are computed fresh on every read
rather than stored alongside the score. **Why:** the `fund_scores` table's
columns are fixed by the schema document, and growing a table to cache three
numbers that are cheap to recompute trades a schema change for nothing.
Consistent with the existing rule that there are no per-user analytics
tables.

## 2026-08-13 — Score tier boundaries are inclusive on the lower bound, not strict

**Why:** the percentile formula in use means the best fund in a
minimum-size category of exactly five schemes lands **exactly on** the top
boundary. A strict comparison would deny the best fund in the category its
top tier, which is indefensible to a user and was called out as a specific
test rather than left to chance.

## 2026-08-13 — The scorer's month-end history window is five years regardless of scheme age

Monthly NAV series are built over a fixed five-year window; schemes with less
history simply have leading gaps. **Why:** this mirrors the already-settled
return rule rather than introducing a second, differently-shaped window
decision. Funds under three years are refused a score entirely, which is the
guard that matters.

## 2026-08-14 — The auth showcase panel is hand-built on existing chart primitives

Because a branch-reality check found **Bklit UI is not installed** — the
component configuration registers its registry as a pull-on-demand source,
but no package exists. Tailwind and shadcn/ui are genuinely in use. **Why:**
building against a library that is not there fails at the first import. The
same day's analytics frontend design assumes Bklit UI *is* available; that
disagreement is R-019 and is unresolved.

## 2026-08-14 — The analytics redesign reuses the existing allocation donut unchanged

A deliberate carve-out from an otherwise wholesale component-library
redesign. **Why:** the design schema's consistent-chart-language rule
outweighs visual consistency with a new component library. A user reading two
charts in the same product should not have to learn two visual vocabularies.

## 2026-08-15 — A transcription error in the auth pill order was corrected by a dated note, not silently

An earlier draft of the 2026-08-14 frontend plan transcribed the auth method
pill order wrongly; the correct order is Google, Apple (disabled), Email,
Phone. **Why:** the plan was corrected on 2026-08-15 with the error recorded
rather than quietly overwritten — the same supersede-in-place rule this vault
applies to its own records, applied upstream in the source material.

## 2026-08-17 — Authentication is passwordless; the same-day reversal is recorded, not hidden

PRD-02 FR-2 was revised twice on this date — to email + password, then reversed to
email + OTP by management decision. Final state: phone + OTP, email + OTP, or Google,
converging on a mandatory verified phone number. Password storage was removed from the
schema by migrations 0007–0008. **Why:** recorded as a reversal rather than a clean
decision because the churn is the useful fact.

## 2026-08-19 — The `LATERAL` optimisation is deferred, with a benchmark attached

The "obviously faster" per-scheme index-seek rewrite of `_bulk_nav_on_or_before` measured
**slower** on the dev dataset (~4.6s vs ~3.5s) and is deferred until it can be measured
on real Postgres. **Why:** the guardrail against coding blind for one dialect cuts both
ways. The measurement is attached so nobody redoes it on faith. See
`07-risks-and-debt.md`.

## 2026-09-02 — The schema document is treated as lagging the migrations, by default

Where `Database-Schema-Unifolio.md` and the code-repo migrations disagree, the migrations
win. **Why:** a compliance audit found the document three to four migrations stale, and a
second pass the same day found an index it had never specified at all.

## 2026-09-16 — PAN storage direction resolved: encrypted at rest, planned future work

Unifolio will store each family member's PAN, encrypted at rest, to support per-member
matching against CAS filings (`Updated-CAS-PRD.md` FR-4). **Why:** resolves R-001, the
open contradiction between that requirement and PRD-01/schema/TDD's "PAN never
persisted." See [ADR-007](ADR-007-pan-storage-and-encryption.md) — direction confirmed,
not yet implemented; no PAN column exists in the schema today.

## 2026-09-17 — R-015 clarified: two fund-score methodologies, not one contradiction

Batch 2a's write pass initially recorded R-015 as an open contradiction
between this vault's two live-looking fund-score formulas. A live
conversation with the vault owner clarified that they are not in conflict:
[ADR-010](ADR-010-fund-scorer-composite-formula.md)'s three-ingredient
composite is the current, live methodology, and a separate methodology based
on per-fund stock-holdings data is planned but blocked pending availability
of that data — a forward-looking initiative, not yet documented anywhere in
the vault. **Why:** no product call is needed to pick a winner between the
two; they are not competing for the same slot. Source: vault owner, live
conversation, 2026-09-17 — not yet corroborated against a written plan or
spec; corroborate against source material if one surfaces in a later batch.
See [R-015](../07-risks-and-debt.md) and the status banner on
[`05-docs/explanation/fund-scoring-methodology.md`](../05-docs/explanation/fund-scoring-methodology.md).

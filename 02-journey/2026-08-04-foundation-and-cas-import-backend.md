# Foundation and CAS Import Backend

Date: 2026-08-04
Status: Complete

## For stakeholders

This is the day the specification set stopped being a document and started
being software. Two pieces of work ran back to back. The first stood up an
empty but correctly-shaped application — the backend, the frontend shell,
the whole database, and a test pipeline that runs against both the database
we develop on and the one we will ship on — deliberately with no features in
it at all. The second took the existing throwaway CAS-parsing prototype,
tightened the parts the product requirements actually depend on (telling
Direct plans from Regular ones, capturing which distributor sold the fund,
and producing error messages a user can act on), moved that logic into the
real application, and then deleted the prototype rather than leaving two
half-alive systems around.

Two useful things surfaced before a line was written. First, a formal
architecture decision recorded in July claimed the work preserved an
in-progress React frontend; checking the actual folder showed it was plain
TypeScript, so the justification was false. It was corrected by amendment,
not by quietly rewriting the record. Second, the old prototype was found to
be storing a masked PAN on two of its tables — something the product's own
rules forbid. Rather than assume it had been carried across, a permanent
guard test was written whose only job is to fail if a PAN column ever
reappears in the real schema. That test is now, as of September, in direct
tension with a later decision to store PANs encrypted; see the note at the
end of this entry.

## Technical detail

### Intended outcome

**Phase 0** — an empty-but-correct skeleton: one FastAPI application with
four empty service packages (`auth`, `import_`, `dashboard`, `analytics`)
matching the TDD's monolith-not-microservices design; one React SPA on Vite
with matching feature folders per ADR-001; the complete
`Database-Schema-Unifolio.md` schema wired through Alembic against both
SQLite (dev) and PostgreSQL (functional-parity); test frameworks on both
sides; and CI running both dialect suites. Explicitly nothing feature-shaped.

**Phase 1** — tighten the standalone CAS-parser prototype's parsing and
matching logic against PRD-01 (Direct/Regular classification, ARN capture,
error-message test coverage), then port the tightened logic into the
monolith's Import Service, and retire the prototype once green.

### What actually happened

Both completed. Phase 0 landed fifteen tables, of which the two the schema
requires to be partitioned on PostgreSQL (`transactions`, `nav_history`)
get dialect-branched DDL while the other thirteen are created directly from
the same SQLAlchemy model metadata on both dialects — one column list, not
two that can drift apart. Migrations are hand-written, never autogenerated,
precisely because autogeneration cannot express the `RANGE (date)`
partitioning branch.

Phase 1 ran in two stages: tighten in place against the prototype's own
pytest suite (no monolith changes), then port into
`backend/app/core/decimal_utils.py`, `backend/app/services/import_/`
(parser, mfapi.in enrichment client, schemas, orchestration service) and
`backend/app/api/imports.py`, targeting Phase 0's UUID-keyed,
`household_member_id`-scoped schema rather than the prototype's integer-PK
one. The prototype backend was then retired. Its frontend was deliberately
left in place as reference material for the Phase 1b UI plan.

Three findings were confirmed before implementation rather than assumed:

1. **ADR-001's stated premise was false.** The prototype frontend at
   `CAS Parsers/mf-import/frontend` is vanilla TypeScript, not React, so
   ADR-001's "avoids rework on in-progress React work" benefit was moot.
   Recorded as an amendment to ADR-001 dated 2026-08-05 — already in this
   vault via batch 1.
2. **The prototype persisted a masked PAN.** `Investor` and `Folio` in the
   prototype's models carried `pan_masked`, contradicting the project's
   no-PAN rule. The target schema has no PAN column on any table; masking
   is used only in the parse-preview response and never written. Phase 1
   Task 9 added a dedicated guard test (`backend/tests/models/test_no_pan_field.py`)
   that fails if any model grows a PAN-shaped column.
3. **The CAS parsing library's field names were verified by installing and
   inspecting the package**, not guessed from documentation — notably that
   the ARN/broker code arrives under a field named `advisor` (the library
   has no field called `arn`), and that the CAMS-vs-KFintech source
   indicator is a different attribute from the Summary-vs-Detailed one.

### Deviation — decision or response taken

| Deviation | Response |
|---|---|
| ADR-001's justification was factually wrong | Amended, not rewritten (see `03-decisions/ADR-001-frontend-application-architecture.md`) |
| Prototype persisted `pan_masked` on two tables | Prototype retired; a permanent regression test added whose only purpose is to fail if a PAN column reappears |
| Two backends would otherwise have run in parallel | Explicit decision to port and delete rather than maintain both — the standalone prototype backend is gone |
| Alembic autogeneration cannot express partitioning | Migrations are hand-written and dialect-branched by policy |
| PostgreSQL's native enum for `transactions.type` is harder to extend than a `VARCHAR` + `CHECK` | Corner cut taken knowingly and marked in code with a `ponytail:` comment naming the ceiling. Recorded as debt (R-022) |

### Result

An application skeleton with the full schema under migration control on both
dialects, CI running both, and a working CAS import API in the real
monolith with the prototype retired. Import Review UI deferred to Phase 1b
as a separate plan, matching the plan/UI split used for every later phase.

Carried forward from this day: no KFintech CAS fixture exists, so KFintech
support is best-effort and unverified against real data — this reinforces
rather than replaces [R-009](../07-risks-and-debt.md). PRD-01's "100%
accuracy" open question was deliberately not answered here on the grounds
that it is a product-definition question, not an engineering one.

**Tension to note.** The no-PAN guard test added on this day now enforces
the opposite of [ADR-007](../03-decisions/ADR-007-pan-storage-and-encryption.md)
(2026-09-16), which decided PANs will be stored encrypted. Implementing
ADR-007 requires deliberately changing a test written to prevent exactly
that. Recorded as [R-018](../07-risks-and-debt.md).
